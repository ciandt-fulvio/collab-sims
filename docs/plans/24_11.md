 Detalhes de Implementação

 Estrutura de Arquivos de Activity Results

 Localização: data/execution/activity_results/{project_name}/

 Naming convention: {activity-script}_{YYYY-MM-DD}.md

 Exemplo: how-might-we_2025-01-15.md

 Estrutura esperada:
 ---
 status: completed
 participants: "Alice, Bob"
 session_id: "uuid-here"
 ---

 # Resultado da atividade How Might We

 [Conteúdo do resultado...]

 Lógica de Matching Activity → Result

 O backend cruza:
 - activity.path do process_type YAML (ex:
 activity_scripts/how-might-we.md)
 - activity_script do arquivo de resultado (ex: how-might-we)

 Match ocorre quando o path termina com {activity_script}.md

 Cálculo de Progresso

 Por Stage:
 - completion_count = número de activities completadas no stage
 - total_activities = número total de activities no stage
 - Percentual = (completion_count / total_activities) * 100

 Geral:
 - Soma completion_count de todos os stages
 - Soma total_activities de todos os stages
 - Percentual geral

 UI/UX Considerations

 - Usar transições suaves (Alpine.js x-collapse)
 - Indicadores visuais claros (cores, ícones)
 - Estado de loading durante fetch
 - Mensagens quando não há dados
 - Auto-expandir primeiro stage ao carregar
 - Cores consistentes com o design system:
   - Project: verde
   - Activities: amarelo
   - Completado: verde
   - Pendente: cinza
   - Required: vermelho
   - Optional: cinza

 Riscos e Mitigações

 Risco 1: Arquivos de resultado não seguem naming convention
 - Mitigação: Regex pattern flexível + logging de arquivos ignorados

 Risco 2: Process type ID não existe ou não tem stages
 - Mitigação: HTTP 404/400 com mensagens claras + mensagem na UI

 Risco 3: Projeto não tem process type definido
 - Mitigação: Mensagem na UI "This project does not have a process type
 defined"

 Risco 4: Nenhum resultado de atividade ainda
 - Mitigação: Mensagem na UI "No activity executions found for this
 project"
